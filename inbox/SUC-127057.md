# SUC-127057 — Live-Triggered Journey with Sleep 2h + App Inbox Failure

Live-triggered journey via API event → `SegmentConsumer` builds SMessage → NB `SegmentStreamManager` applies sleep delay via `PostActionTargetMessageEnqueueUtility` → 2h TimedQueue wait → `ProfileLookupBatchTask` returns no profile for `idn` → `ProfileNotReachable` bounce with `device=Web` → `mapDeviceToDownload(Web, NotificationInbox)` throws `NoSuchFieldException`.

## Upstream — why `iid=0` on the Message

The trigger event is a **CleverTap API `/1/upload` with `identity` only** (no `objectId`/guid, no install context):

```
POST https://eu1.api.clevertap.com/1/upload
{ "d": [{ "identity": "akshat.jain@clevertap.com", "ts": ..., "type": "event",
          "evtName": "TestEvent2", "evtData": {"data": 2} }] }
```

### LC → Redis
LC forwards **only the raw `k` list** — it does **not** resolve identity → `i`/`j`. Sample Redis payload:
```
meta = { a: <account>, lcTs: ..., es: 1, k: ["akshat.jain@clevertap.com"] }
events = [{ t: 2, ts: ..., eName: "TestEvent2", eb: {data: 2} }]
```
No `i`, no `j`, no `g` (guid) in the Redis entry.

### LP `GenericEventProcessor.preConsume` (line 2038)
For a regular `EventType.event`, the K-shard-only path fires:
- Line 2108: `requestI = 0`, `requestJ = 0`, `requestGuid = null`, `requestK = ["akshat..."]`.
- Line 2251-2266: `ShardIdentityUtil.getInfo(0, 0, requestK, null, ...)` — network call to ES for identity resolution.
- Line 2350-2351: `profile.IID = obtainedI`, `profile.IDENTITY = obtainedJ`.

### ES `ShardIdentityUtil.getInfo` (`core/es-base/.../ShardIdentityUtil.java`)
With `requestGuid` blank, falls into the `else if (requestK.size() > 0)` branch at line 287:
- Line 289: `getJ(requestK, hosts, true)` — K-shard lookup returns the existing `j = 2753712` for `akshat.jain@clevertap.com`.
- Line 315-316: `if (j > 0 && requestK.size() == 1) return new Info(i, j, ...)` — **returns with `i` still equal to the initial `0`**.

Why `i=0` is deterministic: **the K-shard schema stores only `k → j`, not `k → i`**. A `j` (identity) can map to zero-to-many installs; there is no unique reverse `j → i` mapping. Only the guid-shard path (SDK requests with a device guid) generates or looks up an `i`. Identity-only API pushes never surface an `i` from this call — by design.

### LP `GenericEventProcessor` line 606-607
```java

ew.event.idn = profile.getLong(ProfilesDao.IDENTITY, 0);  // = 2753712
```

### LP `SegmentConsumer.buildSMessage` line 1123-1127 — the K-shard swap
```java
if (evt.iid == 0 && evt.idn != 0) {
    // if a segment is on some event. And if that event is pushed via API against identity,
    // then we have only idn and iid (K shard).
    evt.iid = evt.idn;
}
```
For our event, this fires: `evt.iid = 2753712`. Only `evt.iid` is serialized into the SMessage at line 1144 / 1154 — `evt.idn` is not carried through separately; the swap makes `iid` carry the identity value into the K-shard routing at ES.

**The `iid=idn` swap is intentional and correct for identity-shard routing** (Push/Browser/Email flows depend on it). The bug surfaces later because NotificationInbox's downstream mapping has no `Device.Web` case.

### Root cause summary

- **Trigger:** identity-only API `/1/upload` event → LC → LP with no `i`/`guid`.
- **LP identity resolution:** `ShardIdentityUtil.getInfo` at ES-side returns `i=0, j=2753712` deterministically (K-shard has no reverse `j → i` mapping).
- **LP SegmentConsumer:** `iid=idn` swap (line 1123-1127) makes SMessage carry `iid=2753712` (the identity value routed to K-shard).
- **NB SegmentStreamManager → PostActionTargetMessageEnqueueUtility:** applies `delay=120` from Mongo → `scheduledForMinute = nowMin + 125`; **iid zeroed, idn kept** (`new Message(..., idn > 0 ? 0 : iid, idn, ...)` at line 83).
- **2h wait**, then `ProfileLookupBatchTask` queries ES with `idnList=[2753712]`, `iidList=[]`.
- **ES returns no matching install profile.** Reason: the ES `/p/ds` handler resolves profiles via install-shard lookup keyed by `i`. A K-shard-only entry (`j=2753712`, `i=0`) has no install record to return via the `idn`-list path. The identity-only user was never bound to a device profile because no SDK event ever arrived with a matching guid — only API-side identity events.
- `message.setProfileNotFoundInLookup(true)` → `processProfileNotFoundInLookUp` → `DispatchResponseHelper.handleError(m, ProfileNotReachable)` with the message's `device=Web` (PRN was encoded as `Mode.Web` at LP).
- `BounceProcessor` reads `mode=NotificationInbox` from `TargetingDao`, `device=Web` from the bounce entity.
- `TargetingEventStoreHelper.mapDeviceToDownload(Web, NotificationInbox)` at line 573-582 has no `Web` case in the `NotificationInbox` switch → throws `NoSuchFieldException`.

### The exact throw

`core/nb/src/com/wizrocket/nb/utils/TargetingEventStoreHelper.java:573-582`
```java
} else if (mode == Mode.NotificationInbox) {
    switch (device) {
```

Push, Browser, Email, SMS, WhatsApp all have `Web` cases. Only `NotificationInbox` doesn't — which is why identity-triggered flows work for every other channel but blow up here.

### Blast radius

- **Stats:** `TargetingCountManager.markError` succeeds before the throw (line 363-364 of `BounceProcessor`) — `profile_not_reachable=1` gets written under device-ordinal key `0` (Web). Observable in `wizrocket.targetingstats`.
- **ES bounce record:** `markAsBounced` throws before `bt.addData(...)` at `TargetingEventStoreHelper.java:249`. **The bounce is never recorded in ES.** For a Journey exit-node target this means the Journey may not properly mark the profile as exited-via-unreachable if it depends on the ES record.
- **Scope:** any Journey App Inbox target reached by an identity-only API trigger against a user without a device install. Not account-specific; not campaign-specific.

### Fix options

**Option A — drop at LP (recommended).** In `SegmentConsumer.buildSMessage`, if `si.tgt.getMode() == NotificationInbox` AND `evt.iid == 0 && evt.idn != 0`, skip the message with a `Profiler.report("Dropping App Inbox trigger — no install context, a: " + accountId)`. App Inbox intrinsically requires an SDK install to render — identity-only routing is meaningless for this channel. Consistent with LP's rule that any drop must have a Profiler counter.

**Option B — add `Web` mapping.** In `TargetingEventStoreHelper.java:573-582`, add `case Web: return Download.notificationInbox;` (enum ordinal 14 already exists in `QueryConstants.Download`). Stops the exception, records the bounce, but semantically weird — records an inbox bounce for a device that can't render an inbox. Useful as a defensive backstop even if Option A is taken.

**Option C — guard the swap.** In `SegmentConsumer.java:1123-1127`, condition the `iid=idn` swap on `si.tgt.getMode() != NotificationInbox` (and any other install-only channels). Preserves Push/Browser/Email K-shard routing untouched.

**Recommended pairing:** A (drop with counter) + B (safety net for any residual path). C alone leaves other install-only channels vulnerable to the same class of bug.

### PR / owner

- NB owners: `TargetingEventStoreHelper.java` (Option B).
- LP owners: `SegmentConsumer.java` (Option A / C).
- Coordinate: the drop message from Option A needs a Profiler metric alert if the count is non-trivial — indicates upstream API callers sending identity-only triggers for App Inbox campaigns.

### Why the filters can't save the SUC-127057 case

Every filter above requires an **install-shard profile** on the ES side to act on:

- `PROFILE_TYPE` (OS) → filters installs by their stored OS.
- `DEVICE_TYPE_LIST` → filters installs by their stored device-type ordinal.
- `sendToAllDevices` toggle → picks single vs. all installs.

The K-shard user in SUC-127057 has **no install-shard entry** — no `ap`, no OS field, no device-type field, no `il` list. The identity was never bound to a device via SDK (no guid ever landed). When NB queries ES with `idnList=[2753712]`:

- If `sendToAllDevices=false`: ES falls into the single-install branch at line 2906. It searches for an install profile keyed by this idn — none exists → `profileNotFoundInLookup=true` → bounce path with `Device.Web`.
- If `sendToAllDevices=true`: ES falls into the multi-install branch at line 2882. `aggregateAllIidsForUidMapOptimized` searches the install linked-list for this uid — nothing there → empty result → `profileNotFoundInLookup=true`. Same outcome.

The filters aren't wrong. They're just downstream of the missing install profile. Any UI change to "Deliver to" cannot fix this — the upstream API trigger has no install context to filter on in the first place.

### `sendToAllDevices=true` — different failure shape if install exists

If the user DID have a real install AND `sendToAllDevices=true`, then:
- ES returns `il` with actual install entries.
- NB fan-out at `InboxStoreManager.java:264-270` creates one message per install.
- `utils.modifyMessage(msg, deviceInfo)` sets each message's iid to the specific install and re-encodes the PRN from that install's `pn`.
- Real Android/iOS installs → `Device.Android`/`Device.iOS` → `mapDeviceToDownload` succeeds.
- BUT: if any install in `il` is identity-typed (e.g. the `dls[2753712]` entry in the incident profile, with `pn:"2753712"` and no mobile app fields) — that install's PRN decodes to `Device.Web` and hits the same `mapDeviceToDownload(Web, NotificationInbox)` throw.

So flipping the target to `sendToAllDevices=true` partially reduces blast radius (real mobile installs go through) but does not fix the underlying bug.

### Enforcement summary

| Filter | LP | NB (request build) | ES (fetch) | NB (post-lookup) | NB (fan-out) |
|---|---|---|---|---|---|
| `device[]` (OS) | — | maps to PROFILE_TYPE | filters installs by ptList | — | — |
| `deviceTypes[]` | — | conditional DEVICE_TYPE_LIST | filters by dts (linked-list-ready + LD flag) | — | — |
| `sendToAllDevices` | — | il=1 when true | multi-install branch when true | copies il onto message | fans out per install when true |

**Net:** ES is the single enforcement point for `device[]` and `deviceTypes[]`. NB and ES both act on `sendToAllDevices`. LP is filter-agnostic — it only produces the identifier NB will later use to query ES.
