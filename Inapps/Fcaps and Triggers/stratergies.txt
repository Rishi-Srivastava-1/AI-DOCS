

private Optional<InAppDelivery> getSS(ProcessParams params) {
        List<InAppDelivery> deliveries = new ArrayList<>();
        if (EventsHelper.inactionDeliveryRequested(params.getEventName(),
                params.getEventProperties())) {
            return Optional.of(deliveryStrategySSInactionContentFetch);
        }

        if (metaDeliveryRequested(params.getEventName(), params.getEventProperties())) {
            // metadata for all SS campaign in-apps (no content)
            deliveries.add(deliveryStrategyMetaSS);
        }

        if (APP_LAUNCHED.equals(params.getEventName())) {
            // special handling for App Launched - return campaigns meta and content or one journey
            deliveries.add(deliveryStrategyAppLaunchedSS);
            // metadata for inaction App Launched campaigns
            deliveries.add(deliveryStrategyAppLaunchedSSMeta);
        } else {
            // content requested from the SDK
            deliveries.add(deliveryStrategySS);
            deliveries.add(deliveryStrategySSInaction);
        }

        if (!params.getInAppSuppressIds().isEmpty()) {
            // App Launched suppressions
            deliveries.add(deliveryStrategySuppressionAppLaunchedSS);
        }

        return MergeDelivery.of(deliveries);
    }

5. DeliveryStrategyAppLaunchedSS

The problem it solves: on the first launch after a campaign is created, the SDK doesn't know the campaign exists — so it can't ask for it via inapps_eval. Solution: on App Launched, push full content for every eligible campaign up front, and let the SDK pick.

Output: inapp_notifs_applaunched (campaigns) or inapp_notifs (one journey).

Targets = APP_LAUNCHED ∪ null-trigger, !CS, targetType == InstantEventClosure, priority ↓ / id ↑.

isFreshLaunch is the extra bit: on a genuine cold start (fresh_launch in the App Launched event) it wipes every prior inaction qualification for the user and re-arms from scratch. Otherwise it only arms timers not already running.

Note it also has no hasAdvancedRules / inapps_eval gate — same reason as AppLaunchedSS: on App Launched the SDK hasn't had a chance to ask.

No control group, no quota — arming a timer isn't a send. Both run later in SSInactionContentFetch.

7. deliveryStrategySuppressionAppLaunchedSS


Closes the loop opened by AppLaunchedSS's suppressed stubs. Emits no payload — only suppression events for LP.


Class is DeliveryStrategySuppressionsCS — CS-era name, reused for SS. Same class also backs DELIVERY_SUPPRESSION_CS.
Targets = DeliveryTargetsAppLaunchedSS (App-Launched ∪ null-trigger, !CS, != InstantEventClosure).
Metered only — no FilteredTargetsProvider. No SDK-capability filtering; you're matching an id the SDK already reported.


The one non-obvious thing

It runs on a non-App-Launched request, but looks up App-Launched targets.

No App Launched event fires after an in-app is shown or suppressed, so the SDK reports the suppression on its next event — Charged, say. The campaign isn't triggered by Charged, so a normal event lookup would miss it. Hence the App-Launched targets provider.
